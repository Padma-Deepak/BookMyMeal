
# 1. Executive Summary
BookMyMeal is a web-based resort meal management platform that digitises the end-to-end food-ordering lifecycle for a single-property resort. It connects Guests, Managers, Caterers, and Caretakers through a single system, replacing manual order-taking and paper bills with a structured, auditable workflow.

Key outcomes the platform delivers:
- Guests can browse a live menu (honouring notice periods and item availability), place orders with dietary preferences, and view a transparent breakdown of their spending.
- Caterers receive instant order notifications, can manage their own offerings, and view their payout history — including itemised invoices and paid/pending status — without any visibility into guest-facing prices.
- Managers have full operational control: they manage caterer accounts, menu items, and pricing; generate and share bills; approve payments; and access complete billing history for both guests and caterers.
- Caretakers handle rejected orders by modifying the guest's order or sourcing items externally, and log all vendor purchases for transparency.

Note on the Superuser role: The Superuser account exists solely as a break-glass technical account for system emergencies (app downtime, data corruption, account lockout). All day-to-day operational responsibilities previously assigned to the Superuser have been transferred to the Manager. The app is designed to run fully without Superuser involvement.

# 4. Functional Requirements
## 4.1 Guest Onboarding
Before a guest can place orders, the Manager creates a guest record at check-in.
- Manager creates a guest record with: full name, phone number (used for WhatsApp bill sharing), check-in date, check-out date.
- The system generates a magic link or PIN sent to the guest's phone number, giving them access to the guest-facing menu and bill views.
- Only one active guest exists at any time (single-occupancy Airbnb-style property). The Manager can deactivate the current guest on checkout and create a new one on the next check-in.
- Guest access is scoped to menu browsing, order placement, and bill viewing only. No administrative actions are available to guests.

## 4.2 Menu Display & Ordering (Guest)
### 4.2.1 Menu Screen
The guest-facing menu screen is the primary entry point for placing food orders. It must reflect real-time item availability and enforce caterer-defined notice periods.
- Display all menu items grouped by meal category (Breakfast, Lunch, Dinner, Snacks, Beverage).
- Show only items marked as available by the assigned caterer; unavailable items are hidden entirely.
- Each item displays the required notice period (e.g. 'Order at least 4 hours in advance') as set by the caterer.
- Items ordered within their notice period are blocked at the UI level with an explanatory message and cannot be submitted.
- Quantity input: numeric stepper per item.
- Spicy preference: dropdown per item — None / Mild / Medium / Hot / Extra Hot.
- Allergies & special preferences: one free-text input field per order (not per item).
- 'Add to Order' button adds selected items to a cart. 'View Order' navigates to the order summary.

### 4.2.2 Order Summary & Submission
- Display a tabular summary of all selected items: name, quantity, spicy level, unit price, line total.
- Show order-level notes (allergies/preferences field).
- Display total cost.
- If the cart contains items from multiple caterers, submission creates one order per caterer automatically. The guest sees a combined confirmation showing each order's status.
- 'Submit Order' calls POST /api/orders/. On success, show confirmation with the maximum prep time across all items in the order.
- 'View Bill' navigates to the guest bill view if a bill has been generated by the manager.

### 4.2.3 Guest Bill View & Spending Breakdown
- Display spending grouped by meal category: Breakfast spent X, Lunch spent Y, Dinner spent Z, etc.
- Show each order with item details, quantities, and cost per line.
- Complimentary items (e.g. included breakfast) are shown at 0 with a 'Complimentary' label.
- External purchases added by the caretaker appear in the bill automatically with a 'Caretaker Purchase' label.
- Bill line-item hierarchy: regular order items at customer price, then caretaker-modified items (flagged 'Modified'), then external purchases (flagged 'Caretaker Purchase').
- Bill is read-only for guests.

## 4.3 Caterer Menu & Availability Management
### 4.3.1 Menu Item Management (Caterer)
Each caterer owns and manages their specific subset of menu items. Default caterer assignment per dish is set by the Manager.
- Caterer can add new menu items: name, description, category, notice period, prep time, and their own caterer price.
- Caterer can remove items from their menu at any time; removed items are immediately hidden from the guest menu.
- Caterer can toggle item availability on/off without removing the item. Only available items appear on the guest menu.
- Caterer can set and edit the notice period per item (in hours/minutes). This is displayed to guests on the menu screen.
- Caterer can set and edit the prep time per item (in minutes). This is used to calculate estimated preparation time shown to guests after order submission.
- Caterer can set and edit their caterer price per item. Customer-facing prices are set and managed by the Manager only. Caterers have no visibility into what guests are charged.

### 4.3.2 Order Notifications & Approval
- When a guest submits an order containing a caterer's items, that caterer receives an instant in-app notification (push notification if supported).
- Caterer Dashboard lists all incoming orders with item details, guest identifier, and order time.
- Pending timeout: if an order is not approved or rejected within 30 minutes, it automatically surfaces in the Caretaker dashboard for follow-up, alongside rejected orders.
- Caterer can Approve an order — status moves to 'Accepted'.
- Caterer can Reject an order — must select a reason: Out of stock / Ingredients unavailable / Preparation not possible today / Insufficient notice period / Other (free-text mandatory). Rejection reason is routed to the Caretaker only, not shown to the guest.

### 4.3.3 Order Preparation Flow
- Accepted orders appear in an 'In Preparation' queue.
- Caterer can mark individual items as prepared using checkboxes.
- 'Complete Order' button finalises the order status as 'Delivered / Ready'.

### 4.3.4 Caterer Payout History
Caterers can view their complete payout history, scoped to their own caterer prices only. Guest-facing prices are never shown.
- Payout history is organised by guest stay (one payout record per stay per caterer).
- Each payout record shows: stay date range (e.g. 'May 12-15'), items prepared during that stay, quantity, caterer price per item, total amount owed, and paid/pending status.
- Tapping a payout record opens the itemised breakdown for that stay.
- Guest name is not shown to caterers. Stays are identified by date range only, to avoid unnecessary data sharing.
- Paid status is updated by the Manager when they upload caterer payment proof. The caterer sees this update in real time.

## 4.4 Caretaker Workflow
### 4.4.1 Rejected & Timed-Out Order Handling
The Caretaker is the resolver for all caterer rejections and timed-out pending orders.
- Caretaker Dashboard shows all orders with status Rejected or Timed-Out, including the caterer-provided reason where available.
- Caretaker contacts the guest offline to discuss alternatives (the system does not mediate this conversation).
- On the 'Resolve Order' screen, the caretaker can: modify items (swap or remove individual items), log an external purchase, or do both for a partially rejected order.
- Untouched items on a partially modified order remain as originally ordered.
- Once the caretaker saves modifications, the guest receives an in-app notification prompting them to review the updated order summary.
- Caretaker receives a push notification when any order is rejected or times out.

### 4.4.2 External Purchase Logging
- Caretaker records: item name, vendor name (free-text with autocomplete from previously used vendor names), quantity, cost, paid status (Yes/No).
- If paid status is No, the cost is automatically added to the guest's bill.
- If paid status is Yes, it is logged for accounting but not charged to the guest.
- Vendor names are stored as text on the external purchase record. Previously used vendor names are suggested via client-side autocomplete. No separate Vendor model or auto-registration system exists in v1.0.
- All external purchase records are visible to the Manager in the guest's bill and order history.

## 4.5 Manager Workflow
### 4.5.1 Manager Dashboard
- Overview of the current active guest: order count, total spend, bill status.
- Quick access to: generate bill, view all orders, view billing history.

### 4.5.2 Caterer & Menu Management (transferred from Superuser)
The Manager has full control over all operational configuration. No Superuser involvement is required for any of the following:
- Create and manage caterer accounts (name, login credentials, contact details).
- Assign default caterers to menu items.
- Set and edit customer-facing prices for all menu items. Caterers cannot see these prices.
- Add, edit, or remove menu items directly (in addition to caterer self-management).
- Create and manage guest records (check-in, check-out, phone number for WhatsApp).

### 4.5.3 Bill Generation
- Select orders by checkbox to include in the bill (allows partial billing, e.g. lunch orders only).
- Bill automatically includes any unpaid external purchases for that guest.
- Optional discount input (amount or percentage) applied at bill level.
- 'Generate Bill' calls POST /api/bills/ — creates a guest bill using customer-facing prices.
- A separate caterer payout is generated per caterer using caterer prices. These are internal records; the caterer sees their payout status in their history view.

### 4.5.4 Bill Sharing via WhatsApp
- Manager taps 'Send via WhatsApp' on any generated bill.
- The system opens a wa.me deep-link pre-populated with the guest's registered phone number and the authenticated PDF bill URL.
- The link points to the existing GET /api/bills/<id>/pdf/ endpoint, protected by standard authentication. No separate hosted URL or 24-hour expiry required in v1.0 (can be added as a security hardening step in v1.1).

### 4.5.5 Payment Approval & Proof Upload
- Manager clicks 'Approve Payment' to mark a guest bill as paid — calls PATCH /api/bills/<id>/.
- Manager uploads a guest payment screenshot (UPI/bank receipt) as proof. Stored in durable private storage.
- For caterer payouts: Manager uploads a caterer payment screenshot proving they paid the caterer. This updates the paid/pending status visible to the caterer in their payout history.

### 4.5.6 Billing History
The Manager has a complete, searchable history of all billing activity, split into two views:
- Guest Billing History: lists all generated bills by stay, showing guest name, stay dates, total amount, bill status (draft/sent/paid), and a link to download the PDF.
- Caterer Payout History: lists all caterer payouts by stay, showing caterer name, stay dates, total amount owed, paid/pending status, and the uploaded payment proof screenshot.
- Both history views are filterable by date range and searchable by name.
- This is the Manager's audit trail for payment disputes — the payment screenshot serves as evidence in both directions.

# 8. Non-Functional Requirements
## 8.1 Performance
- Menu page must load in under 2 seconds on a standard 4G connection.
- Order submission must respond within 3 seconds under normal load.
- PDF bill generation must complete within 10 seconds for bills up to 50 line items.
## 8.2 Reliability
- Order submissions must be idempotent — duplicate submissions (e.g. from double-tap) must not create duplicate orders.
- Payment screenshot uploads must be stored in durable object storage with 99.9% durability SLA.
## 8.3 Security
- Each role has access only to their designated screens and API endpoints; cross-role access is rejected with HTTP 403.
- Caterer payout screens must never surface customer-facing prices. This is enforced at the API level, not just the UI.
- Payment screenshots are stored in private, access-controlled storage — not publicly accessible.
- WhatsApp bill links use the authenticated PDF endpoint. Time-limited URL expiry is deferred to v1.1.
## 8.4 Accessibility & Usability
- All forms must work on mobile browsers without horizontal scrolling.
- Key actions (Submit Order, Approve, Reject) must have touch target sizes of at least 44x44px.
- Caterer rejection reason screen must surface the built-in options prominently before the free-text field.

# 9. Out of Scope (v1.0)
- In-app guest-to-staff messaging — caretaker conversations with guests remain offline.
- Direct online payment processing — payments are recorded, not processed, through the platform.
- Inventory management for caterers — item availability is manual, not stock-driven.
- Multi-property / multi-resort support — v1.0 targets a single resort deployment.
- Native iOS / Android apps — web-responsive UI only.
- Vendor frequency reporting / Vendor data model — deferred to v2. External purchases use a vendor_name text field with client-side autocomplete only.
- Time-limited WhatsApp PDF URLs — deferred to v1.1 as a security hardening step.

# 11. Assumptions
- This is a single-occupancy Airbnb-style property. Only one guest stays at a time. Multi-guest / multi-room support is out of scope for v1.0.
- Each menu item has exactly one default caterer at any given time. Split-caterer items are not supported.
- The Manager performs all initial setup: creating caterer accounts, assigning default caterers to items, and seeding the base menu. No Superuser involvement is needed for any of this.
- Caterer prices are always lower than customer prices (a margin exists on every item). The system enforces this separation at the API level.
- Payment screenshot retention defaults to 7 years pending formal legal review.
- Guests do not need real-time order status tracking in v1.0. They receive a notification if their order is modified and can view the final bill when generated.
- WhatsApp sharing uses the wa.me deep-link mechanism. No WhatsApp Business API integration is required in v1.0.
- Vendor tracking in v1.0 is limited to a text field with client-side autocomplete. A full Vendor model and frequency reporting are deferred to v2.
